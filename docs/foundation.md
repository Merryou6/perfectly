# 基础切片约定

## 已经立住的边界

- `packages/contracts` 是前后端共享的数据契约。字段变化先改这里，再同步两端。
- 身份认证只负责“用户是谁”，社区权限统一进入 `PermissionService`，由平台角色、社区所有者、成员角色和成员状态共同判断。
- JWT 必须对应未撤销、未过期的 `auth_session`；退出只撤销当前会话，修改密码会撤销该用户全部旧会话并签发新令牌。
- 社区、分区、成员、加入申请和帖子各自拥有独立表与模块，不把权限写进帖子表。
- `section` 只是内容分类，不是授权单元；不存在分区管理员。
- 所有帖子必须归属一个社区和一个分区。正文允许后续与附件组合，附件接入时新增附件表，不把媒体路径拼进正文。
- 写接口通过 DTO 做白名单校验，统一下发 `code/message/data/requestId` 响应。
- 社区卡片使用 `community_page + community_page_version`：草稿只存在页面定义中，发布时生成不可变版本，线上页面只读取当前发布版本。
- 卡片 Schema 只允许主视觉、公告、统计和动作四类组件；动作只允许进入发帖、加入社区和浏览帖子。

## 并行开发接口

前端可以先依赖以下稳定部分：

- `@perfectly/contracts` 中的 `User`、`CommunitySummary`、`CommunityDetail`、`Post`、分页和响应类型。
- `docs/api.md` 中已经实现的社区与帖子接口。
- `apps/web/src/services/request.ts` 统一处理令牌、错误提示和响应解包。

后端可以按模块继续补齐：

- `community`：加入申请审核、成员管理和社区设置。
- `posts`：标签、附件关联、检索和审核状态流转。
- `interaction`：评论、回复和评分。
- `file`：存储适配、上传和下载鉴权。
- `moderation`：敏感词兜底、AI 审核结果和人工复核。
- `customization`：自然语言生成卡片、更多白名单组件、事件回调和排行榜。

新增模块只能通过应用服务访问其他模块，不跨模块直接改写对方表。

## 推荐分工

- 前端基础设施：页面路由、请求层、登录态、社区列表与发帖编辑器。
- 后端基础业务：社区/成员、帖子、权限与迁移。
- 扩展模块负责人：先按 `docs/api.md` 和共享契约定义新增接口，再独立实现页面或服务。

当前最小演示只验证“公开浏览 -> 登录 -> 加入 -> 发帖 -> 详情 -> 编辑/删除”。其他能力不要先堆进首页。
